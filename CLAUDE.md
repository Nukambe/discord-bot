# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A monorepo of three independent, unrelated bots that happen to share `util/` helpers and deployment tooling. There is no shared runtime or shared "core" — each app under `apps/` boots its own client and owns its own commands, jobs, and state. The root `index.js` is a vestigial skeleton, not the real entry point for anything.

- **`apps/familygo`** ("MogoBot") — Discord bot for a Monopoly GO Discord server. Scrapes `monopolygo.wiki` (via Playwright, since Cloudflare blocks headless requests) for daily events and posts formatted embeds, runs a gift-rotation reminder cron, and is also shipped as a standalone Windows `.exe` for a non-technical end user.
- **`apps/twitch`** ("nukambot") — Twitch chat bot (`tmi.js`) with slash-command-style `!commands`, a Spotify "Now Playing" panel, and a React/Vite overlay window (OBS-capturable) that the bot process launches and pushes live state into.
- **`apps/nukoko`** — Discord bot for a different server; slash commands plus scheduled jobs (stream notifier, weekend code).

## Commands

```bash
npm install                    # install root deps
npm start                      # runs root index.js (NOT one of the real bots — see Procfile)

# Run an individual bot directly:
node apps/familygo/index.js
node apps/twitch/index.js
node apps/nukoko/index.js

# familygo Windows .exe build (bundles esbuild -> pkg + Playwright Chromium)
npm run build:familygo
# requires: npx playwright-core install chromium   (once, before first build)
# use playwright-core (not the `playwright` package) so the downloaded Chromium
# revision matches the version actually pinned in package-lock.json

# Twitch overlay (React/Vite), run from apps/twitch/web
npm run dev      # vite dev server
npm run build    # vite build

# One-time Spotify OAuth bootstrap for the twitch overlay's Now Playing panel
npm run spotify:auth
```

There is no configured test runner (`npm test` is a stub) and no lint script. Files under `apps/familygo/tests/*.test.js` are plain scripts invoked directly with `node apps/familygo/tests/<file>.test.js`, not run by a framework — they hit the live `monopolygo.wiki` site and print output for manual inspection, they don't assert.

Per project convention ([[Skip build verification]] in memory): don't run `npx vite build` or similar checks after edits — the user verifies live against the running dev server.

## Deployment model

Each bot is a separate Heroku/Procfile process (see `Procfile`): `familygo`, `nukambot` (twitch), `nukoko`. There is one shared `.env` at the repo root; `.env.example` documents every variable across all three apps, grouped by app. `.env` is never delivered through CI — it's provisioned on the target machine directly.

`apps/familygo` has a second, independent distribution path: `.github/workflows/familygo-release.yml` builds a packaged Windows executable on every push touching `apps/familygo/**`, `build/familygo/build.mjs`, `util/**`, or `package.json`, and publishes it as a GitHub release (`familygo-v<run_number>`). That exe self-updates: `apps/familygo/launch.js` is the packaged entry point — it runs `selfUpdate.js` (checks the latest GitHub release, downloads/swaps files, relaunches) *before* `index.js` (the real bot) is ever imported, so an update never races a live-logged-in Discord client. The relaunch goes through `cmd /c start` so the updated instance gets its own console window — the packaged app writes no log file, so anything not printed to a console is simply lost, which is also why the updater logs every outcome rather than only the interesting ones. The same check/install/relaunch pieces (`checkForUpdate`, `installUpdate`, `relaunch` in `selfUpdate.js`) back the admin-only `/update` slash command, which pulls a new release from inside the live bot: it installs, logs the client out, spawns the new exe the same way, and exits, so the relaunched instance's startup check sees the version file already at the new tag and simply starts. `apps/familygo/index.js` is the entry point when running from source (`npm start` equivalent for dev); `launch.js` is only used in the packaged build.

## Cross-app conventions

- **Command modules**: each command file default-exports `{ data: SlashCommandBuilder, execute(interaction), cooldown?, dmPermission?, defaultMemberPermissions? }`. `util/loadCommands.js` recursively walks a `commands/` directory and dynamically imports every `.js` file to build the registry — dropping a new file into `apps/<app>/commands/` is sufficient to register it, no manual index needed (except familygo's packaged build, see below). Both `familygo/index.js` and `nukoko/index.js` implement matching per-command, per-user cooldown and error-reply logic independently (not shared — if you fix a bug in one, check the other).
- **Slash command deployment**: each app has its own `deploy-commands.js`, called once at process startup (`deployCommands()` at the top of `index.js`), registering guild-scoped commands (instant updates, no global-command propagation delay).
- **Packaged builds can't dynamic-`import()`**: `pkg`-bundled executables (`process.pkg` truthy) can't reach the filesystem the way `loadCommands()` expects, so `apps/familygo/commands/index.js` exports a static `staticCommands` array and `index.js` branches: `process.pkg ? loadCommandsFromModules(staticCommands) : await loadCommands(...)`. If you add a familygo command, add it to both the `commands/` directory *and* the static array, or the packaged .exe won't see it.
- **familygo's config/db**: there's no real database — `apps/familygo/db.js` persists config (gift-rotation schedule, daily-post window) as JSON embedded in a marker line (`DB:`) of the latest message in a dedicated Discord channel (`DB_CHANNEL_ID`), and reads it back by fetching that channel's last message. `updateDb()` posts a new message per write (history lives in channel scrollback) and fires `onDbChange` listeners, which `index.js` uses to tear down and reschedule its cron jobs live. The db outgrew Discord's 2000-character message cap once the gift-rotation rosters moved into it, so a db over ~1900 characters is written as a `db.json` **attachment** with the `DB:` line reduced to the sentinel `@db.json`; `readDbFromMessage` understands both shapes, so older inline messages still parse. That reader returns null only when a message genuinely holds no db and *throws* when a sentinel message's attachment can't be downloaded — callers treat null as "nothing here yet" and fall back to `defaultDb()`, so a silent null on a CDN blip would overwrite the live db with seed values.
- **familygo's gift rotation**: who is in the rotation lives in `db.giftRotation.giftees` (selectable — one is chosen per rotation, the rest gift) and `db.giftRotation.gifters` (always gift, never selected), seeded from the env-var pools that used to be hardcoded in `giftRotation.js`. Each entry is `{ id, channel, name }`, where `id` is a Discord snowflake for a real user and a name slug for a member who only exists as a channel — `formatUserRef` mentions the former and prints the latter, which is why both are supported. `/gift-pool add|remove|view` (admin-only) edits the rosters; adding someone to the list they aren't in moves them, since nobody is in both. `poolsFromDb` falls back to the seeded list per key, so a db written before the rosters moved in still rotates the original pool, while an explicitly empty list is honoured. The *cycle* state (who's left to be picked) is separate and still lives in the `STATE:` line of the rotation channel's last message, normalized against the roster on every run — so roster edits take effect immediately without corrupting an in-flight cycle.
- **Scheduling**: `node-cron`, always pinned to `America/New_York` regardless of host timezone. familygo registers **one cron per distinct fire time, not one per job**: `apps/familygo/cronScheduler.js` takes the `JOBS` array in `index.js` — each entry a `{ name, slots(ctx), run(ctx) }` declaring the discrete minutes it wants rather than a cron expression — expands every job's slots against the live config, buckets them by minute, and schedules one task per bucket that awaits that minute's jobs in `JOBS` order. All tasks share one serial queue, so nothing ever runs concurrently even if a job overruns its slot; that is the point, since coinciding jobs used to mean several visible Chrome windows at once. `startScheduler` returns a handle whose `stop()` tears every task down, and `onDbChange` rebuilds the whole set wholesale (times merge and split as config changes, so patching individual tasks is not possible). Adding a scheduled job means appending to `JOBS`; `atTime(hour, minute, days)` and `windowSlots({ start, end, intervalMinutes, days })` build the slot lists, the latter stepping from the start time (so the configured window start is genuinely the first attempt) and rolling onto the next day when a window spills past midnight. familygo's daily-post job attempts every `retryIntervalMinutes` inside a start/end time window and treats "does Discord already have a message containing this date slug" as its own idempotency check. Its free-dice and wiki-news scans follow the same principle via `apps/familygo/alreadyPosted.js`, which scans recent messages in the destination channels for a link's `host/path`: because "already posted?" is answered by Discord rather than local process state, those jobs scan an overlapping today+yesterday window instead of each owning one day, and re-running one is always safe. On top of the channel scan, `db.lastPosts` (see `getLastPosts`/`updateLastPosts` in `db.js`) records the most recent daily-post date slug, free-dice keys, and per-event-type future-events post, so a scheduled run and its manual slash-command twin (`/post-daily`, `/free-dice`, `/future-events`) never double-post each other's work; the `debug` option on those commands bypasses both dedupe layers (and never records) so a test post always goes out. Widen the window rather than adding runs — every wiki fetch opens a *visible* Chrome window on the packaged desktop build (Cloudflare rejects headless, so `fetchWithPlaywright` can't hide it), which makes scan frequency a user-facing budget. That constraint is why the news sweep and the free-dice check are each a single daily run rather than periodic polls: the news sweep at midnight and the free-dice check at 7:30pm ET, fully independent of the daily events post — the shared scheduler is what keeps the free-dice run and the daily-post window opening, which both land on 7:30pm, from opening two browsers at once. The weekly predictions post (`postWeeklyPredictions.js`, manual twin `/weekly-predictions`, keyed in `db.lastPosts.weekly` by the target Monday's date) follows the daily-post retry pattern instead: Sundays at 7:30pm ET it posts the upcoming Monday–Sunday schedule from the wiki's `/events` calendar page (excluding milestone events and tournaments), retrying every 30 minutes through Monday 3:30pm if the calendar doesn't yet list events on both the target Monday and Sunday. It parses the calendar's embedded Next.js flight-data JSON (`getWeeklyEvents.js`), not the DOM cards — only the JSON carries real end *dates* for multi-day events — and those `start_date`/`end_date` values are genuine UTC despite the page displaying them as raw wall times, so everything is converted to `America/New_York` for grouping and display. The event-name → emoji map used by both the daily and weekly posts is shared via `apps/familygo/emojiMap.js` (which also holds the Quick Wins task → emoji map); emoji ids there must match the guild's live emoji list — a re-uploaded emoji gets a new id and the old one renders as literal text. The weekly post's per-event "(30 Mins)" comes from the calendar record's `local_duration`, which is how long one instance of a flash event runs, not the length of its availability window. Missed free-dice links can be caught up manually with the `/free-dice` command, which is safe to re-run thanks to the overlap-plus-dedupe design. Free-dice dedupe can't key off the URL the wiki prints: monopolygo.wiki wraps Scopely's links in its own shortener (`mplygo.wiki/<slug>`) and mints a fresh slug every time it re-lists a card, so the same reward appears under many URLs and users kept getting links they'd already claimed. `apps/familygo/resolveRewardLink.js` follows the redirect chain (`mplygo.wiki/<slug>` → `mply.io/<token>` → `monopolygo://reward-link/<campaign id>`) to unwrap each href to Scopely's own mply.io link — which is what gets posted, so the channel scan is comparing stable URLs — and to the campaign id, which is stored alongside it in `db.lastPosts.freeDice`. It's plain HTTPS (these shorteners answer a bare HEAD), so it costs no Chrome window, and it fails open to the unresolved URL rather than blocking a post. The collectible spoilers post (`postCollectibleSpoilers.js`, manual twin `/spoilers`, posting to the unofficial-spoilers channel) also runs at 7:30pm ET and is the one job whose dedupe Discord *can't* answer: the wiki dates none of its collectibles — its item records carry `{slug, itemId, name, image, ...}` and the category's `releaseDate` is always `$undefined` — so "what's new" is decided by comparing against the item ids remembered per category in `db.lastPosts.spoilers`. Those are the ids that were on page 1 of each `/wiki/<id>-<category>` page at the end of the previous run: the pages are infinite-scroll but newest-first, so page 1 is the only page worth parsing, and the stored list is self-bounding at ~30 ids per category. Don't "simplify" that to a highest-id-seen watermark — ids inside one release wave are interleaved (82255, 82218, 82225, 82256, ...), so a genuinely new item can carry an id below one already recorded. `getCollectibles.js` fetches all three category pages through **one** `fetchManyWithPlaywright` call (one Chrome window, not three) and omits — rather than empties — any category whose page failed, so a bad fetch can't overwrite good state with nothing and silently re-post a whole category; it retries such a category once, since a once-nightly job has no retry window of its own and the wiki intermittently answers with its own gateway-error page. Artwork goes out as message attachments, not embed images: Discord clusters several attachments into a grid (an embed holds one image, four at most) and attachments preserve the source PNGs' alpha, so the icons stay transparent. An item the wiki has listed before Scopely uploaded its art gets "_(image unavailable)_" next to its name — detected by the asset CDN 404ing, since the record always carries the URL the image *will* have — and is recorded as seen like any other, so it is never re-announced once the art lands.
- **Playwright over plain HTTP**: `util/fetchWithPlaywright.js` exists because `monopolygo.wiki` is behind Cloudflare, which challenges headless Chrome even from non-flagged IPs — headed mode is required, so `CHROME_HEADLESS=false` is mandatory on any machine without a virtual display. It resolves the Chrome binary in this order: `CHROME_PATH` env var → bundled `chrome-win/chrome.exe` next to a `pkg` executable → a hardcoded Heroku buildpack path. `fetchManyWithPlaywright(urls, opts)` is the same thing for several pages through a single launch, reusing one tab — a caller needing sibling pages should use it rather than calling `fetchWithPlaywright` in a loop, since each launch is a visible window on the desktop build; it returns null in a failed page's slot instead of throwing, so one bad URL doesn't cost the caller the pages that did load. `fetchWithPlaywright` is now a one-URL wrapper around it.
- **Self-contained util helpers** (`util/`): `dateUtils.js` (EST-aware date slug formatting — familygo posts are keyed off `America/New_York` calendar dates, not UTC), `sanitize.js` (Twitch chat input sanitization), `loadCommands.js`, `outputToFile.js`, `regexUtils.js`. Treat these as shared, app-agnostic — don't put app-specific logic in `util/`.
- **Twitch overlay IPC**: `apps/twitch/lib/overlayProcess.js` starts the Vite dev server for `apps/twitch/web` as a child process and exposes `overlay.push(channel, data)` for the bot to stream live state (chat, now-playing, connection status) into the React app; `launchOverlayWindow.js` opens it in a dedicated browser window for OBS window-capture. Spotify integration (`lib/spotify.js`) is fully optional — leaving `SPOTIFY_CLIENT_ID/SECRET/REFRESH` unset skips the panel without crashing the bot.
