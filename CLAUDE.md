# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A monorepo of three independent, unrelated bots that happen to share `util/` helpers and deployment tooling. There is no shared runtime or shared "core" — each app under `apps/` boots its own client and owns its own commands, jobs, and state. The root `index.js` is a vestigial skeleton, not the real entry point for anything.

- **`apps/familygo`** ("MogoBot") — Discord bot for a Monopoly GO Discord server. Scrapes `monopolygo.wiki` (via Playwright, since Cloudflare blocks headless requests) for daily events and posts formatted embeds, runs a gift-rotation reminder cron, and is also shipped as a standalone Windows `.exe` for a non-technical end user.
- **`apps/twitch`** ("nukambot") — Twitch chat bot (`tmi.js`) with slash-command-style `!commands`, a Spotify "Now Playing" panel, and a React/Vite overlay window (OBS-capturable) that the bot process launches and pushes live state into.
- **`apps/nukoko`** — Discord bot for a different server; slash commands plus scheduled jobs (stream notifier, weekend code). Deployed together with chappelly (below) via `apps/index.js` so both run on one dyno.
- **`apps/chappelly`** — household reminder Discord bot (its own client and token). Every setting it has — the two people it nags (`KING_USER_ID`, `QUEEN_USER_ID`), the reminder channel, the weather location, and the cron list — is a JSON "env" stored in a Discord channel and edited from Discord; only `CHAPPELLY_TOKEN` lives in `.env`. Each env cron posts a reminder mentioning those people with a single confirm button, or — with `job: "weather"` — the day's forecast (see "chappelly" under cross-app conventions).

## Commands

```bash
npm install                    # install root deps
npm start                      # runs root index.js (NOT one of the real bots — see Procfile)

# Run an individual bot directly:
node apps/familygo/index.js
node apps/twitch/index.js
node apps/nukoko/index.js
node apps/chappelly/index.js
node apps/index.js             # nukoko + chappelly in one process (what the Procfile runs)

# familygo Windows .exe build (bundles esbuild -> pkg + Playwright Chromium)
npm run build:familygo
# requires: npx playwright-core install chromium   (once, before first build)
# use playwright-core (not the `playwright` package) so the downloaded Chromium
# revision matches the version actually pinned in package-lock.json

# Twitch overlay (React/Vite), run from apps/twitch/web
npm run dev      # vite dev server
npm run build    # vite build

# One-time Spotify OAuth bootstrap for the twitch overlay's Now Playing panel
npm run spotify:auth
```

There is no configured test runner (`npm test` is a stub) and no lint script. Files under `apps/familygo/tests/*.test.js` are plain scripts invoked directly with `node apps/familygo/tests/<file>.test.js`, not run by a framework — they hit the live `monopolygo.wiki` site and print output for manual inspection, they don't assert.

Per project convention ([[Skip build verification]] in memory): don't run `npx vite build` or similar checks after edits — the user verifies live against the running dev server.

## Deployment model

The `Procfile` now declares a single Heroku process, `nukoko`, which runs `apps/index.js`: a combined entry point that calls `startChappelly()` (exported by `apps/chappelly/index.js`) and then imports `apps/nukoko/index.js`, whose evaluation boots nukoko as usual — so the two bots share one dyno without either app knowing about the other. chappelly only self-boots when its `index.js` is the script being run, and a missing `CHAPPELLY_TOKEN` logs and leaves nukoko running. familygo and nukambot (twitch) are no longer deployed to Heroku (their Procfile entries were removed; the code stays, familygo ships as the Windows exe below). There is one shared `.env` at the repo root; `.env.example` documents every variable across all apps, grouped by app. `.env` is never delivered through CI — it's provisioned on the target machine directly.

`apps/familygo` has a second, independent distribution path: `.github/workflows/familygo-release.yml` builds a packaged Windows executable on every push touching `apps/familygo/**`, `build/familygo/build.mjs`, `util/**`, or `package.json`, and publishes it as a GitHub release (`familygo-v<run_number>`). That exe self-updates: `apps/familygo/launch.js` is the packaged entry point — it runs `selfUpdate.js` (checks the latest GitHub release, downloads/swaps files, relaunches) *before* `index.js` (the real bot) is ever imported, so an update never races a live-logged-in Discord client. The relaunch goes through `cmd /c start` so the updated instance gets its own console window — the packaged app writes no log file, so anything not printed to a console is simply lost, which is also why the updater logs every outcome rather than only the interesting ones. The same check/install/relaunch pieces (`checkForUpdate`, `installUpdate`, `relaunch` in `selfUpdate.js`) back the admin-only `/update` slash command, which pulls a new release from inside the live bot: it installs, logs the client out, spawns the new exe the same way, and exits, so the relaunched instance's startup check sees the version file already at the new tag and simply starts. `apps/familygo/index.js` is the entry point when running from source (`npm start` equivalent for dev); `launch.js` is only used in the packaged build.

## Cross-app conventions

- **Command modules**: each command file default-exports `{ data: SlashCommandBuilder, execute(interaction), cooldown?, dmPermission?, defaultMemberPermissions? }`. `util/loadCommands.js` recursively walks a `commands/` directory and dynamically imports every `.js` file to build the registry — dropping a new file into `apps/<app>/commands/` is sufficient to register it, no manual index needed (except familygo's packaged build, see below). Both `familygo/index.js` and `nukoko/index.js` implement matching per-command, per-user cooldown and error-reply logic independently (not shared — if you fix a bug in one, check the other).
- **Slash command deployment**: each app has its own `deploy-commands.js`, called once at process startup (`deployCommands()` at the top of `index.js`), registering guild-scoped commands (instant updates, no global-command propagation delay).
- **Packaged builds can't dynamic-`import()`**: `pkg`-bundled executables (`process.pkg` truthy) can't reach the filesystem the way `loadCommands()` expects, so `apps/familygo/commands/index.js` exports a static `staticCommands` array and `index.js` branches: `process.pkg ? loadCommandsFromModules(staticCommands) : await loadCommands(...)`. If you add a familygo command, add it to both the `commands/` directory *and* the static array, or the packaged .exe won't see it.
- **familygo's config/db**: there's no real database — `apps/familygo/db.js` persists config (gift-rotation schedule, daily-post window) as JSON embedded in a marker line (`DB:`) of the latest message in a dedicated Discord channel (`DB_CHANNEL_ID`), and reads it back by fetching that channel's last message. `updateDb()` posts a new message per write (history lives in channel scrollback) and fires `onDbChange` listeners, which `index.js` uses to tear down and reschedule its cron jobs live. The db outgrew Discord's 2000-character message cap once the gift-rotation rosters moved into it, so a db over ~1900 characters is written as a `db.json` **attachment** with the `DB:` line reduced to the sentinel `@db.json`; `readDbFromMessage` understands both shapes, so older inline messages still parse. That reader returns null only when a message genuinely holds no db and *throws* when a sentinel message's attachment can't be downloaded — callers treat null as "nothing here yet" and fall back to `defaultDb()`, so a silent null on a CDN blip would overwrite the live db with seed values.
- **familygo's gift rotation**: who is in the rotation lives in `db.giftRotation.giftees` (selectable — one is chosen per rotation, the rest gift) and `db.giftRotation.gifters` (always gift, never selected), seeded from the env-var pools that used to be hardcoded in `giftRotation.js`. Each entry is `{ id, channel, name }`, where `id` is a Discord snowflake for a real user and a name slug for a member who only exists as a channel — `formatUserRef` mentions the former and prints the latter, which is why both are supported. `/gift-pool add|remove|view` (admin-only) edits the rosters; adding someone to the list they aren't in moves them, since nobody is in both. `poolsFromDb` falls back to the seeded list per key, so a db written before the rosters moved in still rotates the original pool, while an explicitly empty list is honoured. The *cycle* state (who's left to be picked) is separate and still lives in the `STATE:` line of the rotation channel's last message, normalized against the roster on every run — so roster edits take effect immediately without corrupting an in-flight cycle.
- **Scheduling**: always `America/New_York` regardless of host timezone. familygo and chappelly run their own minute ticker (`cronScheduler.js` in each app — chappelly's is a copy), **not node-cron**: node-cron 4 fires each expression from one long timer and only runs the task if it lands with the second hand on :00, and on the Windows desktop build those timers routinely land a second late, which it logs as a "missed execution" and skips — silently, for an expression's first fire since boot — so a whole 7:30pm slot once went by with the process up and nothing running. Only nukoko's `weekendCode.js` still calls `cron.schedule` directly. `apps/familygo/cronScheduler.js` takes the `JOBS` array in `index.js` — each entry a `{ name, slots(ctx), run(ctx) }` declaring the discrete minutes it wants rather than a cron expression — expands every job's slots against the live config, buckets them by minute, and ticks once a minute: each tick settles every UTC minute since the previous one, reads each as an ET slot (walking the clock minute by minute is what makes it DST-proof), and runs every job that had a slot in that span — at most once per job, in `JOBS` order — so a late timer, a stalled event loop or a machine asleep over a slot all resolve the same way. The startup log still prints the schedule as cron expressions, purely as a readable summary. All runs share one serial queue, so nothing ever runs concurrently even if a job overruns its slot; that is the point, since coinciding jobs used to mean several visible Chrome windows at once. `startScheduler` returns a handle whose `stop()` halts the ticker, and `onDbChange` rebuilds the whole set wholesale (times merge and split as config changes, so patching individual tasks is not possible). familygo's boot call passes `{ catchUp: true }`, which runs once every job whose slot for today has already passed (`missedJobs`) — a bot started at 8:12pm no longer sits out the 7:30 slot — and that flag reaches `run` as `ctx.catchUp`; every job dedupes before doing any work so a redundant catch-up is a cheap no-op, except the gift rotation, which can't be re-run and checks its channel for today's log message (`rotatedToday`) when the flag is set. chappelly's copy has no catch-up, since a reminder has no "already posted?" check to make a second run harmless. Adding a scheduled job means appending to `JOBS`; `atTime(hour, minute, days)` and `windowSlots({ start, end, intervalMinutes, days })` build the slot lists, the latter stepping from the start time (so the configured window start is genuinely the first attempt) and rolling onto the next day when a window spills past midnight. familygo's daily-post job attempts every `retryIntervalMinutes` inside a start/end time window and treats "does Discord already have a message containing this date slug" as its own idempotency check. Its free-dice and wiki-news scans follow the same principle via `apps/familygo/alreadyPosted.js`, which scans recent messages in the destination channels for a link's `host/path`: because "already posted?" is answered by Discord rather than local process state, those jobs scan an overlapping today+yesterday window instead of each owning one day, and re-running one is always safe. On top of the channel scan, `db.lastPosts` (see `getLastPosts`/`updateLastPosts` in `db.js`) records the most recent daily-post date slug, free-dice keys, and the news sweep's `newsSweep` cursor, so a scheduled run and its manual slash-command twin (`/post-daily`, `/free-dice`, `/future-events`) never double-post each other's work; the `debug` option on those commands bypasses both dedupe layers (and never records) so a test post always goes out. Widen the window rather than adding runs — every wiki fetch opens a *visible* Chrome window on the packaged desktop build (Cloudflare rejects headless, so `fetchWithPlaywright` can't hide it), which makes scan frequency a user-facing budget. That constraint is why the news sweep and the free-dice check are each a single daily run rather than periodic polls, both at 7:30pm ET alongside the daily-post window opening — the shared scheduler is what keeps them from opening several browsers at once. The news sweep (`postFutureEvents.js`, manual twin `/future-events`) doesn't measure "new" by calendar date: the wiki's "Today's Events (<date>)" posts land on the index at irregular hours, so it uses them as day markers instead. `db.lastPosts.newsSweep` holds the marker the last run stopped at (`cutoff`) and the posts newer than it that were already handled (`searched`, keyed by URL *and* index publish time, since the wiki republishes articles in place with a new date); a run considers every article newer than the cutoff, drops the searched ones, channel-scans the rest, fetches all surviving pages through one `fetchManyWithPlaywright` call, and only advances the cutoff to the newest marker when every candidate resolved, so a failed page fetch is retried next run. A post's identity is the index href, never the article's JSON-LD `url` — a republished `-2` article carries the old article's metadata. Each article goes out as `# title` (route emoji on both ends) with the hero and standalone images stacked as embeds across as many messages as needed, then one `## heading` message per in-article gallery (`figure.pw-gallery`, an album preview's wheels of sticker sets) with the gallery's images as attachments so Discord clusters them into a grid. The weekly predictions post (`postWeeklyPredictions.js`, manual twin `/weekly-predictions`, keyed in `db.lastPosts.weekly` by the target Monday's date) follows the daily-post retry pattern instead: Sundays at 7:30pm ET it posts the upcoming Monday–Sunday schedule from the wiki's `/events` calendar page (excluding milestone events and tournaments), retrying every 30 minutes through Monday 3:30pm if the calendar doesn't yet list events on both the target Monday and Sunday. It parses the calendar's embedded Next.js flight-data JSON (`getWeeklyEvents.js`), not the DOM cards — only the JSON carries real end *dates* for multi-day events — and those `start_date`/`end_date` values are genuine UTC despite the page displaying them as raw wall times, so everything is converted to `America/New_York` for grouping and display. The event-name → emoji map used by both the daily and weekly posts is shared via `apps/familygo/emojiMap.js` (which also holds the Quick Wins task → emoji map); emoji ids there must match the guild's live emoji list — a re-uploaded emoji gets a new id and the old one renders as literal text. The weekly post's per-event "(30 Mins)" comes from the calendar record's `local_duration`, which is how long one instance of a flash event runs, not the length of its availability window. Missed free-dice links can be caught up manually with the `/free-dice` command, which is safe to re-run thanks to the overlap-plus-dedupe design. Free-dice dedupe can't key off the URL the wiki prints: monopolygo.wiki wraps Scopely's links in its own shortener (`mplygo.wiki/<slug>`) and mints a fresh slug every time it re-lists a card, so the same reward appears under many URLs and users kept getting links they'd already claimed. `apps/familygo/resolveRewardLink.js` follows the redirect chain (`mplygo.wiki/<slug>` → `mply.io/<token>` → `monopolygo://reward-link/<campaign id>`) to unwrap each href to Scopely's own mply.io link — which is what gets posted, so the channel scan is comparing stable URLs — and to the campaign id, which is stored alongside it in `db.lastPosts.freeDice`. It's plain HTTPS (these shorteners answer a bare HEAD), so it costs no Chrome window, and it fails open to the unresolved URL rather than blocking a post. The collectible spoilers post (`postCollectibleSpoilers.js`, manual twin `/spoilers`, posting to the unofficial-spoilers channel) also runs at 7:30pm ET and is the one job whose dedupe Discord *can't* answer: the wiki dates none of its collectibles — its item records carry `{slug, itemId, name, image, ...}` and the category's `releaseDate` is always `$undefined` — so "what's new" is decided by comparing against the item ids remembered per category in `db.lastPosts.spoilers`. Those are the ids that were on page 1 of each `/wiki/<id>-<category>` page at the end of the previous run: the pages are infinite-scroll but newest-first, so page 1 is the only page worth parsing, and the stored list is self-bounding at ~30 ids per category. Don't "simplify" that to a highest-id-seen watermark — ids inside one release wave are interleaved (82255, 82218, 82225, 82256, ...), so a genuinely new item can carry an id below one already recorded. `getCollectibles.js` fetches all three category pages through **one** `fetchManyWithPlaywright` call (one Chrome window, not three) and omits — rather than empties — any category whose page failed, so a bad fetch can't overwrite good state with nothing and silently re-post a whole category; it retries such a category once, since a once-nightly job has no retry window of its own and the wiki intermittently answers with its own gateway-error page. Artwork goes out as message attachments, not embed images: Discord clusters several attachments into a grid (an embed holds one image, four at most) and attachments preserve the source PNGs' alpha, so the icons stay transparent. An item the wiki has listed before Scopely uploaded its art gets "_(image unavailable)_" next to its name — detected by the asset CDN 404ing, since the record always carries the URL the image *will* have — and is recorded as seen like any other, so it is never re-announced once the art lands.
- **chappelly's env and crons**: `apps/chappelly/env.js` is familygo's `db.js` pattern (newest `ENV:` message in channel `1552074366307536989`, inline JSON or an `env.json` attachment past ~1900 chars, a new message per write) with two deliberate differences: it scans back up to 50 messages for the marker so a stray chat message can't make the bot re-seed defaults, and it caches the live env in memory (`currentEnv()`) because autocomplete and button clicks read it constantly. `writeEnv(client, mutate)` serializes read-modify-writes and fires `onEnvChange`, which `index.js` uses to rebuild the whole cron schedule. Values are addressed by dotted path (`crons.neema-pill.times`) via `getPath`/`setPath`/`deletePath`/`listPaths`; `/env set` parses JSON only for values that look like objects, arrays, booleans or null and keeps everything else — including bare digits — as strings, because every id in the env is a snowflake and `JSON.parse` would silently round it. Crons are data, not code: each entry under `env.crons` is `{ enabled, job?, times: ["HH:mm" ET], days: [0-6], channel, message, gif, mentions, button, everyDays?, lastRun?, location?, feeds?, runOnStart?, dates?, image? }` and becomes one scheduler job. *Which* job is data too — `job` names a runner in `jobs/registry.js`, and adding a kind of post means a new module listed there, not a change to `index.js`, `cronScheduler.js` or `/cron`, all of which go through the registry. `jobs/common.js` holds what every runner shares: channel/mention resolution and `prepareRun` (load the cron from the live env, apply the `everyDays` gate). `runOnStart: true` additionally fires a cron once as the bot boots (`runBootJobs` in `index.js`, run before the ticker starts so a boot seconds before the hour can't race its own slot) — only a job that can tell it has already posted may use it, which is why the scheduler itself still has no catch-up. Three kinds exist:
  - **`reminder`** (the default when `job` is unset, which is what every cron written before job types existed is) — post `message` (and `gif` on its own line, so Discord unfurls it, and `image` — a file name in `apps/chappelly/media/`, set with `/cron image` — as an attachment; a file rather than a URL because Discord attachment URLs are signed and expire) mentioning `mentions` (env key names like `KING_USER_ID`, or raw user ids; an unset key is dropped rather than printed) with one confirm button.
  - **`weather`** (`jobs/weather.js`) — post today's forecast as an embed (current temp/conditions, high–low, rain chance, wind, an hourly strip of the hours still ahead, sunrise/sunset), with `message` as an optional line above it and no button, since there is nothing to confirm. The place is the cron's `location` or the env-wide `WEATHER_LOCATION`, and `WEATHER_UNITS` picks imperial (default) or metric. `weather.js` (app-level, not `util/`) is the API layer: **Open-Meteo**, chosen because it needs no API key — a keyed provider would put a secret back in `.env` and mean a redeploy to rotate it, in a bot whose whole point is being configurable from Discord. It takes `"lat,lon"` straight through and otherwise geocodes the typed name (cached per process; `"City, ST"` is split so the part after the comma picks among matches — postal abbreviations are expanded to the `admin1` names Open-Meteo returns, since it answers "Maryland", not "MD", and a region the results don't match throws rather than falling back to the top hit, which is how "Abingdon, MD" once became Abingdon, VA). Each request retries transient failures (5xx, 429, timeouts, dropped connections, a non-JSON body) three times half a minute apart before giving up, because the cron gets one shot a day and a single 503 at 07:00 once cost the whole day; a 4xx is thrown at once. A fetch that still fails throws so the scheduler logs it and the next day's slot retries — there is nothing useful to post instead, and an embed of em-dashes would read as real data. The seed env has a `weather` cron at 07:00 ET daily; on a live env, `/cron add id:weather job:weather` creates one and `WEATHER_LOCATION` still has to be set with `/env`.
  - **`news`** (`jobs/news.js`) — post whatever is new in the cron's `feeds`, one embed per article (source, headline linked, summary, thumbnail, section/byline footer, publish time), batched into messages under Discord's caps of 10 embeds and 6000 embed characters; `message` is an optional line above the first batch, and like weather it carries no button and no mentions — there is nothing to confirm and nobody to nag. `feeds` entries are preset keys from `FEED_PRESETS` in `news.js` (`npr`, `patch-belair`, `bbc`, `guardian`, `baltimore-banner`, `wbal`, `wjz`) or raw feed URLs, so adding a paper is an `/env` edit. `news.js` (app-level, like `weather.js`) is the API layer: **plain RSS/Atom over HTTPS**, chosen for the same reason as Open-Meteo — every keyed news API would put a secret back in `.env` and mean a redeploy to rotate it. Deliberately *not* Google News RSS, which is otherwise the best local aggregator: its article links stay on `news.google.com` and only unwrap in JavaScript (a `curl -L` ends on the Google URL with a 200), so posts would carry a redirect Discord can't unfurl and the channel scan can't compare. **Dedupe is Discord's job, not stored state**: every post puts the article URL on its embed and each run reads the destination channel's last 100 messages back and skips those URLs — familygo's `alreadyPosted.js` principle — which is what makes the job safe to run hourly, by hand, and again at boot; remembering posted links in the env instead would write a fresh env message every hour. `maxAgeHours` (48 by default) is the second half of that: an article has to be both unseen *and* recent, so a feed republishing its backlog can't flood the channel even if the scan window has slid past it. Query strings are stripped before posting, not just before comparing — Patch mints a fresh `utm_*` block for every link it hands out, so the raw href would look new every run; `cleanUrl` posts the stripped link and `urlKey` drops a leading `www.` for comparison *only*, since a host that needs its www would 404. Artwork lives in a different element per feed (Patch uses `media:thumbnail`, NPR the first `<img>` of `content:encoded` — skipping the RSS tracking pixel it ends every item with), and a feed that fails is logged and skipped so one dead source doesn't cost the others; only every feed failing throws. Reading the channel needs Read Message History there, which is a REST fetch of the bot's own messages and so doesn't depend on the client's intents. The seed env has a `news` cron reading `npr` + `patch-belair` hourly with `runOnStart: true`; `/cron add id:news job:news` creates one, whose fifth modal input is the feed list in place of a button label. Filtering isn't implemented — every item in a feed goes out, including Patch's statewide `across-md` syndication and its listicles.

`everyDays` makes a cron an interval: its slot still fires at every configured time, but the job posts only once `everyDays` days have passed since `lastRun` (an ET date) and then stamps `lastRun` with today via `recordCronRun`, a *silent* env write that doesn't rebuild the schedule — which is why `runReminder` reads `currentEnv()` rather than the scheduler's ctx snapshot. Gating on days-since-last-post (not a fixed modulus) means a slot missed while the bot was down posts at the next one, and `/cron reset` is simply "stamp lastRun with today". `dates` (`[1, 15]`, typed as `1st, 15th, last` in the modal's Days box in place of weekdays) pins a cron to days of the month the same way: the scheduler's slots are weekly, so a dated cron fires daily and `prepareRun` drops every other day, with a date past the month's end clamped to its last day (31 = "last"). `/cron run` forces past both gates and never stamps, so a test post can't shift the cadence; `/cron gif` swaps the gif. The button's customId carries only the cron id, and who may press it is resolved from the live env at click time, so reminders survive restarts and env edits; pressing it removes the button and stamps who confirmed and when. `/cron add|edit` is a modal (five text inputs is the cap, so the id, channel, interval and job type are slash options and ride in the modal customId; a weather cron spends its fifth input on the location instead of a button label); `/env` is the escape hatch that can reach any field, and either path rebuilds the schedule. The scheduler (`cronScheduler.js`) is a copy of familygo's minute ticker (see "Scheduling" above), minus the startup catch-up; slots are `America/New_York` wall times, so 06:00 stays 6am Eastern across DST without any adjustment.
- **Playwright over plain HTTP**: `util/fetchWithPlaywright.js` exists because `monopolygo.wiki` is behind Cloudflare, which challenges headless Chrome even from non-flagged IPs — headed mode is required, so `CHROME_HEADLESS=false` is mandatory on any machine without a virtual display. It resolves the Chrome binary in this order: `CHROME_PATH` env var → bundled `chrome-win/chrome.exe` next to a `pkg` executable → a hardcoded Heroku buildpack path. `fetchManyWithPlaywright(urls, opts)` is the same thing for several pages through a single launch, reusing one tab — a caller needing sibling pages should use it rather than calling `fetchWithPlaywright` in a loop, since each launch is a visible window on the desktop build; it returns null in a failed page's slot instead of throwing, so one bad URL doesn't cost the caller the pages that did load. `fetchWithPlaywright` is now a one-URL wrapper around it.
- **Self-contained util helpers** (`util/`): `dateUtils.js` (EST-aware date slug formatting — familygo posts are keyed off `America/New_York` calendar dates, not UTC), `sanitize.js` (Twitch chat input sanitization), `loadCommands.js`, `outputToFile.js`, `regexUtils.js`. Treat these as shared, app-agnostic — don't put app-specific logic in `util/`.
- **Twitch overlay IPC**: `apps/twitch/lib/overlayProcess.js` starts the Vite dev server for `apps/twitch/web` as a child process and exposes `overlay.push(channel, data)` for the bot to stream live state (chat, now-playing, connection status) into the React app; `launchOverlayWindow.js` opens it in a dedicated browser window for OBS window-capture. Spotify integration (`lib/spotify.js`) is fully optional — leaving `SPOTIFY_CLIENT_ID/SECRET/REFRESH` unset skips the panel without crashing the bot.
